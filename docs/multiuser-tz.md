# ТЗ: переход «Remember» к многопользовательской модели

Статус: черновик для планирования. Автор: Агент-Планировщик.
База анализа: `README.md`, `AGENTS.md`, весь код `app/`, тесты `tests/`.
Ограничение этапа: только планирование; код и существующие тесты не меняются.

---

## 1. Цель и границы

### Что меняется

1. Данные учёта становятся **изолированными по владельцу**: серверы
   (`Server`), подписки (`Subscription`), разовые расходы (`OneTimeExpense`),
   платежи (`Payment`) видны и изменяются только их владельцем.
2. **Telegram привязывается к пользователю**: пользователь указывает свой
   числовой `telegram_id` в вебе; бот шлёт дайджесты и обрабатывает команды
   только по данным владельца чата. Кнопка «Оплачено ✓» создаёт платёж за
   владельца. Способ привязки — **единственный**: ввод `telegram_id` в
   `/settings` (решение пользователя; см. §6).
3. **Роль `admin`** — решение пользователя: **строгая изоляция данных**
   (admin видит только свои серверы/подписки/расходы/платежи, как любой
   пользователь) + административные функции (управление пользователями,
   бэкапы, настройки приложения). Вариант «admin видит всё» — **не
   реализуем**.
4. **Саморегистрация**: новая открытая страница `/register`, пользователь
   создаёт аккаунт с ролью `user` (подробно — §5).

### Что остаётся общим (глобальным)

- **Настройки приложения** (`settings` таблица, `app/services/settings.py`):
  времена дайджестов, `remind_soon_days`, бот (`bot_enabled`), SOCKS5-прокси,
  бэкапы, `tz`. Один набор на инсталляцию, как сейчас.
- **Планировщик** APScheduler: один на процесс; слоты morning/evening/backup
  глобальные (`app/scheduler.py`), отправка внутри слота уже будет
  per-subscriber (см. §4).
- **Бэкапы** SQLite — вся БД целиком (`app/services/backup.py`), админ.
- **Пользователи и роли**: управление учётками — admin (как сейчас,
  `app/routers/web.py:852`). Тема интерфейса уже per-user (`users.theme`) —
  остаётся.
- **Сессии, пароли (argon2), подпись cookies** — без изменений.

### Что НЕ входит в рамки доработки

- Перенос владельца позиции между пользователями (owner immutable).
- Per-user часовой пояс и валюта.
- Привязка TG через код `/bind` или вручную админом — отклонено решением
  пользователя (§6).

## 2. Модель данных (по таблицам)

### `users` (`app/models.py:25`)

Добавить колонки:

| Колонка | Тип | Ограничения | Назначение |
| --- | --- | --- | --- |
| `telegram_id` | `BigInteger` | `unique=True, nullable=True` | Числовой id TG-аккаунта пользователя; `unique` даёт связь 1:1 «один аккаунт TG ↔ один пользователь» |
| `telegram_id_confirmed` | `Boolean` | `default=False, nullable=False` | Флаг двухшагового подтверждения привязки (§6): `True` — владелец TG подтвердил, что чат его; `False` — ожидает подтверждения, дайджесты/команды с данными не работают |

Колонки bind-кода (`bind_code_hash`/`bind_code_expires_at`) **не нужны** —
способ привязки `/bind <код>` отклонён решением пользователя.

**Валидация `telegram_id`**: положительное целое, в диапазоне int64
(`0 < id < 2**63`). В вебе вводится строкой → преобразование в `int`
с проверкой; на уровне pydantic — новое поле в схеме профиля
(`telegram_id: int | None` + `field_validator` на положительность).
При сохранении проверить, что значение не занято другим пользователем
(иначе ошибка «этот Telegram уже привязан к другому аккаунту»).
AIogram отдаёт `message.from_user.id` как `int` — дополнительной валидации
не нужно, но диапазон проверить.

**Правило смены**: любое изменение `telegram_id` (установка или замена)
сбрасывает `telegram_id_confirmed = False` — привязку надо подтвердить заново
(см. §6).

### `servers` (`app/models.py:42`)

- Добавить `owner_id: Mapped[int] = mapped_column(ForeignKey("users.id", ondelete="CASCADE"), nullable=False)`.
- **Убрать глобальный** `unique=True` у `name` (строка 48) и заменить на
  составной: через `__table_args__` —
  `UniqueConstraint("owner_id", "name", name="uq_servers_owner_name")`.
- Причина: сейчас имя уникально глобально, два разных владельца не смогут
  завести «сервер GPU-1» — после доработки уникальность имён нужна только
  в рамках одного владельца.

### `subscriptions` (`app/models.py:68`)

- Аналогично `servers`: `owner_id` NOT NULL FK `users.id ON DELETE CASCADE`;
  `name` unique → `UniqueConstraint("owner_id", "name", name="uq_subscriptions_owner_name")`.

### `one_time_expenses` (`app/models.py:90`)

- Добавить `owner_id` NOT NULL FK `users.id ON DELETE CASCADE`.
- Уникальности по `title` не было и не нужно. Добавить индекс по
  `owner_id` (`index=True`) для фильтрации списка.

### `payments` (`app/models.py:104`) — отдельная проработка

**Рекомендация: `owner_id` НЕ добавлять, владелец выводится через target.**

Обоснование:

1. **Единственный источник правды.** Платёж всегда привязан к
   `(target_type, target_id)`. Если владелец меняется (в будущем), при
   денормализации пришлось бы синхронно обновлять все платежи; при выводе
   через target рассинхрон невозможен в принципе.
2. **Безопасность обеспечивается на доступе к target.** `mark_paid` /
   `mark_paid_once` (`app/services/billing.py:48,86`) принимают `owner_id` и
   проверяют `target.owner_id == owner_id` ДО записи платежа — чужие платежи
   физически не создаются (см. §4). То же для роутов и бота.
3. **Фильтрация списка платежей по владельцу** — один ORM-запрос с
   подзапросами по target (нагрузка копеечная, индексы по
   `(target_type, target_id)` уже есть через `uq_payment_target_due`):

   ```python
   from sqlalchemy import and_, or_, select
   owned_server_ids = select(Server.id).where(Server.owner_id == uid)
   owned_sub_ids = select(Subscription.id).where(Subscription.owner_id == uid)
   where = or_(
       and_(Payment.target_type == "server",
            Payment.target_id.in_(owned_server_ids)),
       and_(Payment.target_type == "subscription",
            Payment.target_id.in_(owned_sub_ids)),
   )
   ```

4. **Жизненный цикл** согласован: при удалении сервера/подписки удаляются и
   их платежи (`app/routers/web.py:445,556`), поэтому «мёртвых» платежей без
   владельца не бывает.

Альтернатива (если UNION-подзапросы покажутся неудобными в коде): добавить
`payments.owner_id` (nullable) и проставлять ровно в одном месте — в
`mark_paid`. Минусы: дублирование факта, риск рассинхрона. **Не рекомендуется
в v1.**

### `bot_subscribers` (`app/models.py:138`)

- Добавить `user_id: Mapped[int | None] = mapped_column(ForeignKey("users.id", ondelete="SET NULL"), nullable=True, index=True)`.

**Решение «сколько чатов у одного пользователя»:** в v1 привязка работает
**только через личный чат**, где `chat_id == users.telegram_id` (групповые
чаты не поддерживаются — привязывать их нечем). Поэтому у пользователя
ровно один «основной» чат-идентичность — его `telegram_id`; `user_id` в
`bot_subscribers` служит кэшем привязки (проставляется при подтверждении и в
`/start`) и нужен для digest-рассылки. Уникальность `chat_id` сохраняется,
`user_id` — без `unique` (технически одна запись на пользователя, но
гарантия не требуется).

### Индексы и уникальность — итог

| Объект | Изменение |
| --- | --- |
| `servers` | удалить unique(name); добавить `uq_servers_owner_name(owner_id, name)` |
| `subscriptions` | удалить unique(name); добавить `uq_subscriptions_owner_name(owner_id, name)` |
| `one_time_expenses` | добавить `ix_one_time_expenses_owner_id` |
| `payments` | без изменений |
| `users` | `telegram_id` unique index |
| `bot_subscribers` | index на `user_id` |

## 3. Миграция существующей БД

### Механизм: ALTER-подход, без alembic и без пересоздания таблиц

Обоснование:

- Таблицы создаются только через `Base.metadata.create_all`
  (`app/db.py:33-36`) — существующие таблицы `create_all` **не меняет**,
  значит нужен отдельный шаг приведения схемы.
- **Пересоздание таблиц** (rename + create + copy) — рискованно на live:
  сложный перенос FK и `sqlite_sequence`, требует простоя. Оправдано только
  когда нужно навесить `NOT NULL` на колонку с существующими данными без
  дефолта — в нашем случае все новые колонки пустые, данные backfill'ятся.
- **ALTER** добавляет только новые колонки и индексы; старые данные
  сохраняются. SQLite 3.37+ поддерживает `ALTER TABLE ... ADD COLUMN`
  (в т.ч. с `REFERENCES`). Ограничение: колонку нельзя добавить с `NOT NULL`
  без `DEFAULT` → добавляем **nullable**, а жёсткость переносим на уровень
  ORM и приложения (см. ниже).

### Точки вызова

1. `init_db()` — `create_all` (создаёт новые таблицы, если их нет).
2. `ensure_admin_user()` (`app/auth.py:104`) — гарантирует существование
   admin (нужен для backfill).
3. Новая `async def migrate_schema(session)` — в `app/db.py` (проект
   маленький, отдельный модуль не обязателен; решение за исполнителем),
   вызывается из `app/main.py:60-63` после `ensure_admin_user`.

### Алгоритм `migrate_schema` (идемпотентный)

Для каждой таблицы определить существующие колонки через
`PRAGMA table_info(<t>)` и существующие индексы через `PRAGMA index_list(<t>)`.

1. **Добавить отсутствующие колонки** (`ALTER TABLE ... ADD COLUMN`):
   - `users.telegram_id BIGINT`,
     `users.telegram_id_confirmed BOOLEAN NOT NULL DEFAULT 0`;
   - `servers.owner_id INTEGER REFERENCES users(id) ON DELETE CASCADE`;
   - `subscriptions.owner_id INTEGER REFERENCES users(id) ON DELETE CASCADE`;
   - `one_time_expenses.owner_id INTEGER REFERENCES users(id) ON DELETE CASCADE`;
   - `bot_subscribers.user_id INTEGER REFERENCES users(id) ON DELETE SET NULL`.
   Все — nullable (см. выше), кроме `telegram_id_confirmed` (добавляется с
   `DEFAULT 0` — для существующих строк это корректно: никто ещё не
   привязывался).
2. **Backfill владельца**: `UPDATE <table> SET owner_id = :admin_id
   WHERE owner_id IS NULL`, где `admin_id` =
   `SELECT id FROM users WHERE role='admin' ORDER BY id ASC LIMIT 1`,
   fallback — первый пользователь по `id` (если admin'а нет).
   Применяется к `servers`, `subscriptions`, `one_time_expenses`.
3. **Индексы**:
   - удалить глобальный unique-индекс имени, если существует (обычно
     `ix_servers_name` / `ix_subscriptions_name`) — `DROP INDEX`;
   - создать `CREATE UNIQUE INDEX uq_servers_owner_name ON servers(owner_id, name)`
     и то же для подписок;
   - `CREATE UNIQUE INDEX uq_users_telegram_id ON users(telegram_id)`
     (все NULL — для SQLite это ок);
   - `CREATE INDEX ix_bot_subscribers_user_id ON bot_subscribers(user_id)`;
   - `CREATE INDEX ix_one_time_expenses_owner_id ON one_time_expenses(owner_id)`.
4. **Дубликаты имён**: существующие имена глобально уникальны (был unique),
   все строки получают одного владельца ⇒ `(owner_id, name)` не может
   конфликтовать. Если вдруг создание unique-индекса упадёт (IntegrityError —
   аномальная БД) — залогировать, создать обычный индекс и продолжить;
   починить имена вручную. Это задокументировать в коде.
5. **Версионирование**: записать `settings.schema_version = "2"`, чтобы
   будущие изменения шли по порядку, а `migrate_schema` могла пропускать
   уже применённые шаги.

### ORM vs физическая схема

В моделях `owner_id` объявлен `nullable=False` — SQLAlchemy требует значение
при INSERT. В существующей БД колонка физически останется nullable; приложение
всегда проставляет владельца. Навешивание `NOT NULL` на БД потребовало бы
пересоздания таблиц — не делаем в v1 (задокументировать комментарием в
`models.py`).

### Файлы задачи

`app/models.py`, `app/db.py`, `app/main.py` (вызов миграции), `tests/test_migration.py`.

### `app/bot/sender.py`

- `send_digest_to_subscribers` (строка 52). Сейчас: один digest на всех
  активных подписчиков. Новая логика:
  1. Выбрать активных подписчиков **с привязанным пользователем**
     (`BotSubscriber.user_id IS NOT NULL`, JOIN на `User`).
  2. Сгруппировать чаты по `user_id`, для каждого пользователя построить
     digest один раз: `collect_digest(session, today, soon_days, owner_id=user.id)`.
  3. Отправить каждому чату digest его владельца.
  4. Чаты без `user_id`: **не получают дайджест** (не спамим; подсказка —
     только в момент команд/`/start`, см. §6).
- `send_evening_reminder_to_subscribers` (строка 66) — аналогично: overdue
  считается per-user, отправляется только в чаты привязанных пользователей
  с непустым списком просрочки.
- Контракт с планировщиком не меняется: sender вызывается как
  `await sender(factory=factory)` (`app/scheduler.py:171`, регистрация в
  `app/bot/manager.py:98-99`).

### Что возвращается непривязанному/неподтверждённому чату

Для команд `/today`, `/soon`, `/overdue`, `/list`, `/add`, `/subscribe` и
pay-колбэков, если для чата не найден привязанный пользователь с
подтверждённым `telegram_id` (см. §6) — один текст-подсказка:

> «Чтобы я показывал ваши данные, привяжите аккаунт: войдите в веб-интерфейс
> → Настройки → Telegram, укажите свой ID (узнать: напишите @userinfobot) и
> подтвердите привязку в этом чате.»

`/start`, `/help` работают всегда.

Digest-рассылка (`sender.py`): чаты без `user_id` ИЛИ с пользователем, у
которого `telegram_id_confirmed = False`, **пропускаются** (не спамим).

### Профиль / привязка Telegram (блок на `/settings`)

- Текущий статус: «Привязано к <telegram_id> (подтверждено)» /
  «Привязано к <telegram_id> — ожидает подтверждения» / «Не привязано».
- Поле ввода numeric `telegram_id` + сохранение (валидация и правило смены —
  §2). При установке/смене сервер:
  1. сохраняет `telegram_id` и сбрасывает `telegram_id_confirmed = False`;
  2. если бот запущен и в БД есть `BotSubscriber.chat_id == telegram_id` —
     бот отправляет в этот чат уведомление с inline-кнопкой «Подтвердить»
     (механизм §6);
  3. в `/settings` показывается предупреждение «Ожидает подтверждения —
     нажмите „Подтвердить“ в Telegram» и кнопка **«Отвязать»**
     (очистить `telegram_id`).
- Справка: как узнать свой telegram_id (через @userinfobot).

### Саморегистрация `/register`

- Открытые роуты `GET /register` (форма) и `POST /register` (создание),
  **без** зависимости `get_current_user` (неавторизованный доступ).
- Форма: `username` (1–64, уникальный), `password` (мин. 4, max 128),
  `confirm` (совпадение с password). Валидация — через существующую схему
  `UserCreate` (`app/schemas.py:17`).
- Создаётся пользователь с `role="user"` (никогда не `admin`). Первый
  зарегистрировавшийся admin'ом **не** становится: admin создаётся как
  сейчас — `ensure_admin_user` из `ADMIN_PASSWORD` env при первом запуске
  (`app/auth.py:104-134`).
- После успешной регистрации — автоматический логин (те же шаги, что в
  `login_submit`, `web.py:282-305`) и редирект на `/`.
- **Защита от спама** (адекватно самохостed-приложению, без внешних
  зависимостей):
  - уникальность `username` (IntegrityError → «пользователь уже существует»,
    как в `create_user`, `web.py:897-904`);
  - валидация длины/совпадения пароля (форма + `UserCreate`);
  - простой in-memory rate-limit по IP: словарь `{ip: [timestamps]}`, макс.
    N попыток (рекомендуется 5) за 15 минут → 429 «Слишком много попыток.
    Попробуйте позже»; сбрасывается при перезапуске процесса (для

- `is_active = True` по умолчанию; admin может менять роль и активность в

## 6. Бот и привязка TG

### Принятый способ привязки

**Единственный способ (решение пользователя):** пользователь вводит свой
числовой `telegram_id` в вебе (`/settings`). Способы `/bind <код>` и ввод
вручную админом — отклонены.

Работает это так: бот связывает чат с пользователем по совпадению
`chat_id == users.telegram_id` (в личных чатах Telegram `chat_id ==
from_user.id`). `users.telegram_id` уникален ⇒ один TG-аккаунт нельзя
привязать к двум пользователям; `bot_subscribers.chat_id` уникален ⇒ чат
привязан максимум к одному пользователю.

### Защита от «указал чужой id» — двухшаговое подтверждение

Чтобы чужой человек (или ошибка) не увел дайджесты на чужой аккаунт:

1. Пользователь вводит `telegram_id` в `/settings` → сервер сохраняет его и
   ставит `telegram_id_confirmed = False`.
2. **Бот отправляет в чат с этим `chat_id` уведомление** (если такой
   `BotSubscriber` существует в БД и бот запущен):
   > «К вам привязан аккаунт <username> в Remember. Если это вы — нажмите
   > „Подтвердить“. Если нет — нажмите „Отменить“.»
   + inline-кнопки **«Подтвердить»** и **«Отменить»** (callback-префиксы
   `tg_confirm:<user_id>` / `tg_cancel:<user_id>`, новые в `keyboards.py`).
3. **«Подтвердить»** → `telegram_id_confirmed = True`,
   `BotSubscriber.user_id = <user_id>` (создать подписку, если чата ещё нет),
   `is_active = True`. Дайджесты и команды с данными начинают работать.
   **«Отменить»** → сервер очищает `telegram_id` пользователя (привязка
   отклонена владельцем чата).
4. Пока `telegram_id_confirmed = False`: дайджесты не шлются, команды
   `/today`/`/soon`/`/overdue`/`/list`/`/add` в этом чате отвечают
   подсказкой «подтвердите привязку» (см. §4).
5. Если бот был выключен или чата ещё не было — ничего не отправляется;
   в `/settings` висит статус «ожидает подтверждения» + кнопка «Отвязать»
   (очистить `telegram_id`). При следующем `/start` из этого чата бот
   повторно шлёт уведомление (или привязывает автоматически, см. ниже).
6. Смена `telegram_id` в вебе сбрасывает подтверждение (§2) — цикл
   повторяется.

Дополнительная страховка: в `cmd_start` (`handlers.py:106`) бот проверяет
`users.telegram_id == chat_id`; если у пользователя `telegram_id_confirmed =
True`, но `BotSubscriber.user_id` не проставлен — привязка восстанавливается
автоматически (кэш не расходится с фактом).

Ограничение принятого способа: привязка работает только для **личных чатов**
(групповые чаты не идентифицируемы этим способом) — это осознанное решение.

### Команды, требующие привязки

- **Требуют** подтверждённой привязки (данные владельца): `/today`, `/soon`,
  `/overdue`, `/list`, `/add`, `/subscribe`, `/unsubscribe`, pay-колбэки.
- **Не требуют**: `/start`, `/help`, `/cancel`.
- Непривязанному/неподтверждённому чату — подсказка из §4.

### Кнопка «Оплачено ✓» и `/add`

- `on_pay` (`handlers.py:379`): владелец чата = привязанный пользователь
  (см. ниже); target проверяется на владельца через
  `mark_paid_once(..., owner_id=uid, paid_by=uid)`; непривязанный чат —
  подсказка.
- `/add` (`handlers.py:241`, создание 325/335): создаёт Server/Subscription с
  `owner_id = user.id` владельца чата.

### Определение владельца чата

Новый хелпер `_owner(session, message) -> User | None` в `handlers.py`:

1. `BotSubscriber` по `chat_id`; если `user_id` установлен — вернуть
   пользователя (при условии `telegram_id_confirmed == True`).
2. Иначе — `User` по `telegram_id == chat_id`; если найден и подтверждён —
   проставить `BotSubscriber.user_id` (кэш) и вернуть.
3. Иначе — `None` (подсказка).

### Точечные правки `app/bot/handlers.py`

| Место (строка) | Изменение |
| --- | --- |
| `_section_response` (89) | `collect_digest(..., owner_id=user.id)` из владельца чата; нет владельца — подсказка |
| `_list_text` (171) | фильтры `Server.owner_id == uid`, `Subscription.owner_id == uid` |
| `/add` (241; создание 325/335) | `owner_id = user.id` владельца чата; нет владельца — подсказка до старта FSM |
| `on_pay` (379) | target проверить на владельца (через `mark_paid_once(..., owner_id=uid, paid_by=uid)`); нет владельца — подсказка |
| `cmd_start` (106) | если `users.telegram_id == chat_id` (подтверждён) — приветствие с username и «дайджесты придут сюда», восстановить `BotSubscriber.user_id`; если `telegram_id` задан, но не подтверждён — повторно отправить уведомление с кнопками; иначе — подсказка |
| `/subscribe`/`/unsubscribe` (126/138) | требуют подтверждённой привязки; `/subscribe` лишь включает `is_active` |
| новые `tg_confirm`/`tg_cancel` | callback-обработчики кнопок подтверждения/отмены (п. 3 выше) |

`bot_subscribers` остаётся хранилищем подписок чатов; `user_id` проставляется
при подтверждении привязки и в `/start` — `/subscribe` лишь
включает/выключает `is_active`.

## 7. Безопасность и краевые случаи

- **Проверка прав на каждый объект**: единый путь —
  `_get_target` в `billing.py` с проверкой `owner_id` + во всех роутах выборка
  по `(id, owner_id)`. Чужой id → 404.
- **Сервис как барьер**: `mark_paid`/`mark_paid_once` сами проверяют владельца —
  защита действует даже если какой-то вызывающий слой «забудет» проверку.
- **Удаление пользователя** (`delete_user`, `web.py:962`), последовательность:
  1. Существующие проверки («нельзя удалить себя», «последнего admin») —
     сохранить.
  2. `UPDATE payments SET paid_by = NULL WHERE paid_by = :uid` — уже есть,
     оставить.
  3. `DELETE FROM payments WHERE (target_type='server' AND target_id IN
     (SELECT id FROM servers WHERE owner_id=:uid)) OR (target_type='subscription'
     AND target_id IN (SELECT id FROM subscriptions WHERE owner_id=:uid))` —
     убрать платежи владельца до удаления позиций.
  4. Удалить `one_time_expenses`, `servers`, `subscriptions` владельца
     **явно** (не полагаться на `ON DELETE CASCADE`: SQLite не включает
     enforcement FK по умолчанию).
  5. `UPDATE bot_subscribers SET user_id = NULL WHERE user_id = :uid` —
     чаты не спамятся дайджестами после удаления аккаунта.
  6. `DELETE FROM users WHERE id = :uid`.
  - Опционально (рекомендуется): включить `PRAGMA foreign_keys=ON` в
    `app/db.py` при создании engine — тогда каскады сработают и как страховка;
    перед включением прогнать тесты (порядок удаления payments→target уже
    корректный, `web.py:445,556`).
- **Инъекции**: подтверждение — все запросы через ORM/параметры
  (`sqlalchemy.select`, `text` с bind-параметрами для миграции); новых
  f-string SQL не вводить.
- **Секреты**: секретов привязки нет (нет bind-кодов); токен бота — только
  env (`app/config.py`); пароль прокси не логируется
  (`app/services/settings.py:278`); `telegram_id`/статусы в логи не писать.
- **Краевые случаи**:
  - Пользователь `is_active=False` — дайджесты не шлются (JOIN на активного
    пользователя), команды → «аккаунт отключён»/подсказка.
  - Подписчик ссылается на удалённого пользователя — JOIN отсекает, мусор
    не шлётся.
  - Смена `telegram_id` в вебе сбрасывает `telegram_id_confirmed` (§2):
    старый чат перестаёт получать дайджесты, новый — ждёт подтверждения.
  - Пользователь нажал «Отменить» в уведомлении — `telegram_id` очищается,
    повторное уведомление не шлётся до новой попытки в вебе.
  - Гонка двух `mark_paid_once` → уникальный constraint `uq_payment_target_due`
    + идемпотентность (механизм уже есть, `billing.py:63-69`).
  - Часовой пояс — глобальный (`settings.tz`), digest считается по нему
    (`app/bot/handlers.py:59`).

## Развёртывание

Целевой сервер: **185.221.213.96** (домен **rem.homebug.ru**), код — в
`/opt/remember`, запуск через systemd (`deploy/remember.service`).

### Подготовка (обязательно перед обновлением)

1. **Ручной бэкап БД** на сервере: `sqlite3 data/remember.db ".backup
   data/backups/pre-multiuser-$(date +%F).db"` (или через веб `/backups`).
2. Перенести код: `git pull` (или замена файлов) в `/opt/remember`.

### Запуск и миграция

1. Перезапустить сервис: `systemctl restart remember`.
2. Миграция выполняется **автоматически при старте** `main.py`: порядок
   `init_db()` → `ensure_admin_user()` → `migrate_schema()` (§3).
   - Существующая БД содержит данные admin'а — backfill присвоит все
     серверы/подписки/расходы **admin'у**, т.е. данные не теряются и
     остаются видимыми под прежним логином admin.
   - `migrate_schema` **идемпотентна**: повторный запуск — no-op; при сбое
     на любом шаге приложение падает до старта веб-сервера, БД остаётся в
     неизменном состоянии (ALTER выполняется по одному, каждый шаг
     проверяет наличие колонки/индекса).
3. Проверить логи: `journalctl -u remember -f` — нет ошибок миграции.

### Контрольный список после деплоя

- [ ] `/login` (admin) работает; на дашборде — все прежние серверы/подписки
      (владелец = admin).
- [ ] Создать тестового пользователя через `/register`, убедиться в изоляции
      (тестовый пользователь не видит данные admin).
- [ ] Привязать Telegram: `/settings` → ввести `telegram_id` → подтвердить
      кнопкой в боте; приходит утренний дайджест только своих данных.
- [ ] Настройки (`bot_enabled`, прокси), бэкапы, `/users` — работают.

### Откат

При критической ошибке: `systemctl stop remember` → восстановить код
прошлой версии → восстановить БД из шага «Подготовка» →
`systemctl start remember`. Никакие данные не теряются, т.к. миграция
работает только «вперёд» от текущей схемы.
