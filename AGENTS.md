# AGENTS.md — правила работы агентов (многоагентная среда)

Любая разработка в этом репозитории выполняется по ролям
**Оркестратор → Исполнитель → Ревьюер → основной поток**. Это правило обязательно
для всех агентов, включая основной.

## Роли

### Оркестратор (основной агент)
- Держит план работ (todo-лист) и декомпозирует задачи.
- Пишет детальные ТЗ для подагентов-исполнителей.
- Запускает ревьюера после каждой реализации.
- Вливает результат в основную линию **только** после вердикта «ok».
- Не выполняет крупную реализацию сам; прямая правка допустима лишь для
  мелких фиксов по итогам ревью.

### Исполнитель (subagent, Task tool)
- Получает ТЗ с указанием файлов, моделей данных и границ задачи.
- Перед стартом читает `README.md` и этот файл.
- Реализует строго в рамках своего ТЗ, не трогая чужие области.
- Ничего не коммитит, не деплоит, не шлёт сообщений пользователю.
- В финальном ответе возвращает: список созданных/изменённых файлов,
  как проверял работу, какие решения принял сверх ТЗ.

### Ревьюер (subagent, Task tool)
- Проверяет результат исполнителя по чек-листу ниже.
- Возвращает вердикт `ok` | `not-ok` и список замечаний с `файл:строка`.
- При `not-ok` оркестратор возвращает ТЗ исполнителю на доработку
  (цикл повторяется до `ok`).

## Процесс

1. Оркестратор декомпозирует фичу на задачи и заводит todo.
2. Ставит ТЗ исполнителю (с ожидаемым возвратом — см. «Роли/Исполнитель»).
3. Исполнитель реализует и проверяет (тесты/линт — см. «Проверки»).
4. Оркестратор ставит ревьюеру проверить результат.
5. Если `not-ok` — доработка исполнителем, повторное ревью.
6. После `ok` — оркестратор интегрирует в основной поток и закрывает todo.

## Чек-лист ревьюера

- [ ] Реализация соответствует ТЗ и решениям из `README.md`.
- [ ] Пользовательские параметры не захардкожены: всё через настройки в БД
      (`app/services/settings.py`); секреты — только из окружения (`app/config.py`).
- [ ] Бизнес-логика корректна: перенос `next_due` от исходной даты, digest,
      суммы, идемпотентность «Оплачено ✓».
- [ ] Безопасность: пароли хэшируются (argon2), сессии подписаны, SQL — через
      ORM/параметры, в репозиторий не попадает `.env` и секреты.
- [ ] Конвенции: Python 3.11+, типизация, docstring на публичные функции/классы,
      минимум комментариев, код проходит `ruff`.
- [ ] Тесты на бизнес-логику есть и проходят.
- [ ] `README.md` актуален (обновлён, если поведение изменилось).

## Сквозные правила

- Секреты и токены никогда не попадают в файлы, коммиты, логи.
- `.env.example` — шаблон; реальный `.env` и `data/` — в `.gitignore`.
- `_unnecessary/` — карантин лишних/временных файлов (в `.gitignore`);
  не коммитится, чистится вручную, всё внутри безопасно удалять.
- Одна задача — одно изменение: не смешивать несвязанные правки.
- Не менять файлы вне своей области без явного указания оркестратора.
- Код только на английском в идентификаторах; текст пользовательских сообщений —
  на русском.
- Все даты с часовым поясом (`tz` берётся из настроек); «сегодня» считается по нему.
- При изменении архитектуры/процесса — обновить `README.md` и этот файл.

## Проверки перед сдачей работы

```bash
python -m pytest -q
ruff check .
```

Исполнитель обязан прогнать обе команды и сообщить результат. Ревьюер может
запустить их повторно.
